# 03 · 质量门禁 G0–G6（门禁引擎 / 软硬门 / 阈值治理 / gate_result 制品）

> 04-治理域第 3 篇。定位：**治理者视角**——门禁作为治理裁决怎么编排、签批、留痕、治阈值。边界：G0–G6 的位置/检查项/阈值/失败处理 = [算子设计-02](../02-生产域/算子设计/算子设计-02-算子接口规范与质量门体系.md) §9（**SSOT，本篇不重抄那张表**）；版本生命周期状态机 = [01-版本管理与不可变快照](01-版本管理与不可变快照.md) §5（本篇门禁是其状态迁移的触发器）；G6 回归门展开 = [05-回归与发布](05-回归与发布.md)；G5 泄漏检查细节 = [06-数据分流与防泄漏](06-数据分流与防泄漏.md)；违规拦截的合规策略来源 = [07-合规引擎](07-合规引擎.md)；回流通道 = [管控域 DLQ](../03-管控域/03-任务状态机与容错.md)。

## 1. 定位与边界

- **本篇管**：门禁的**裁决面**——门怎么编排（谁先谁后）、结果怎么持久化（gate_result）、软硬怎么分、阈值怎么治、豁免怎么走、误判怎么衡量
- **不管**：检查项与阈值定义（算子-02 §9）、检查在哪个算子出口执行（算子-02 §9 位置列）、回归怎么跑（05）、血缘怎么提供证据（[02](02-血缘制品与版本三锁.md)）
- **一句话**：算子-02 §9 定义「门长什么样」，本篇定义「门怎么当裁判」——裁判要持证（规则签批）、留笔录（gate_result）、有量刑标准（阈值治理）、允许上诉（豁免工单）

## 2. 核心概念与组件

| 组件 | 职责 | 要点 |
| --- | --- | --- |
| 门禁引擎（Gate Engine） | 编排 G0–G6 执行、汇总、裁决 | 治理域组件「质检网关」（总线 §3④） |
| gate_result 制品 | 每次判定的持久化凭证 | §4；挂血缘图（[02 §3](02-血缘制品与版本三锁.md) Gate 结果节点） |
| 软门 / 硬门 / 源头门 | 失败处理分级 | §5 |
| 阈值注册表 | 阈值集版本化管理 | §6；改阈值 = 变更，走评审 |
| 豁免工单 | 例外放行的唯一通道 | §6；有期限、可追责 |

> **与负载均衡治理同构**：门禁引擎 ≈ 配置下发前的合法性检查 + 变更审批流——自动门是规则引擎秒判（schema/ACL 校验），发布门是 CAB 人工审批；gate_result ≈ 审批工单留痕。我在 XLB 天天过的就是这套：**下发前拦住，判定留凭证，例外走工单**。

## 3. 门禁在治理流中的位置（编排）

```
生产域执行 ──阶段出口──► G0–G4（算子/阶段级 · 自动门 · 规则签批）
                            │ 全过                        │ 失败
                            ▼                            ▼
                     Validated（01 §5）          拦截 / 回流 / 人工介入
                            │                    （回流通道 = 管控域 DLQ）
                            ▼
                  G5 封装门（泄漏=0）──► G6 回归门（Golden 无倒退，05 展开）
                            │                        │
                            ▼                        ▼
                     发布审批（人工签批，05）──────► Published（01 §5，不可变）
```

- **执行与裁决分工**：G0–G4 在生产域算子出口执行（算子-02 §9），**裁决汇总在治理域**——引擎拉取各门实测、比对阈值、出 verdict
- **签批分工**：自动门（G0–G5）= **规则签批**（引擎 + 阈值集版本即可追责）；发布门（G6+审批）= **人工签批**（05 §5）
- **失败回流闭环**：失败 → 血缘定位（[02 trace_badcase](02-血缘制品与版本三锁.md)）→ 重跑 / 人工修复 / 模型修复 → 重新过门——门禁不是终点站，是回流闭环的起点（总线 §6 #8）

## 4. gate_result 制品（判定凭证）

```yaml
gate_result:                       # 设计通识（字段以实现为准）
  gate_id: G2                      # G0–G6（定义见算子-02 §9）
  gate_version: 1.3.0              # 阈值集版本（§6——判定依据可追溯）
  target: {dataset_version: v3.1.0, batch_id: b-20261017, node: l2-perception}
  checks:                          # 记实测值（下列数值为示例）；阈值定义以算子-02 §9 为准
    - {check: 重建成功率,   threshold: ">=0.95", measured: 0.962, pass: true}
    - {check: 分层抽检一致率, threshold: ">=0.95", measured: 0.970, pass: true}
    - {check: 通吃率,       threshold: ">=0.90", measured: 0.910, pass: true}
  verdict: pass | fail | pass_with_waiver     # 豁免放行（§6）
  decided_at: ...
  decided_by: {kind: rule | human, ref: gate-engine@v… | approver_id}
  evidence_ref: {qc_report: ..., lineage_query: get_lineage(v3.1.0)}
```

- **为什么必须制品化**：verdict 会随版本晋升被反复引用（05 发布检查清单要引用 G6 的 gate_result）——判定不可复查 = 裁决不可追溯
- **挂血缘图**：gate_result 是图上节点（02 §3），「v3.1.0 过了 G2」本身可被 blast radius 查询波及

## 5. 软门与硬门（量刑分级）

| 类别 | 门 | 失败处理 | 理由 |
| --- | --- | --- | --- |
| **源头门** | G0 接入 / G1 预处理 | 拦截 + 重采/重跑/降级帧 | 最省 GPU——缺陷拦得越早越便宜（[总线 §7](../00-总体架构/README.md) ADR「质量门前置」） |
| **软门** | G2 结构化 / G3 语义 | 人工介入 / 回流模型 / 修正后重试 | 质量问题**可修复**，允许再来 |
| **硬门** | G4 违规率=0 / G5 泄漏=0 / G6 回归倒退 | 全批拦截 / 拦截修复 / 版本回滚 | 合规与泄漏**不可带瑕流转**（G6 的回滚语义见 05 §6） |

- **假阳与假阴**：假阳（误拦）成本 = 重跑算力；**假阴（漏放）代价更大**——污染下游版本与训练，且要靠事后泄漏审计/回归才发现。两个错误率随阈值此消彼长，调整阈值必须两边一起看（§6）
- **G4/G5 无豁免通道**：质量阈值可以豁免（带期限），违规与泄漏**不存在「先放后补」**——这是 [06](06-数据分流与防泄漏.md) / [07](07-合规引擎.md) 两篇的共同前提

## 6. 阈值治理（判例法，不是拍脑袋）

- **阈值即配置**：默认建议值可配置（算子-02 §0 已声明）；阈值集**自身版本化**（gate_version）——改阈值 = 变更，走评审 + 版本发布，禁止线上手改
- **豁免（例外放行）**：必须走审批工单——记录豁免理由、责任人、**期限**；到期自动失效重新拦截；禁止静默放行。豁免案件量是门禁健康度的反向指标（§7）
- **抽检的统计依据**：分层抽检比例必须有样本量/置信度依据（分层方法见 [标注体系-02 §4](../02-生产域/标注体系/02-标注质检与来源标记.md)）——「抽检通过」必须能回答「抽了多少、什么分层、置信度多少」，否则无统计意义
- **阈值校准回路**：假阳/假阴估计（复核被拦样本 + 抽查已放行样本）→ 反馈阈值调整 → 新 gate_version——门禁自身也要迭代

## 7. 指标与质量门（元指标——门禁自身的健康度）

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| 各 Gate 拦截率分布 | 每个门的拦截占比 | 定位薄弱阶段（G1 高=接入质量差，G3 高=VLM 短板） |
| 假阳率 / 假阴率估计 | 误拦 / 漏放的估计值 | 阈值校准（§6）；待团队标定 |
| 豁免次数 / 逾期未处理数 | 例外治理健康度 | 豁免滥用告警；逾期自动重拦 |
| 门禁判定时延 | 实测汇总到 verdict | 应秒级，不成生产瓶颈 |
| gate_result 完整率 | 判定留凭证比例 | **100%（无留痕的通过 = 没通过）** |

## 9. 红线与面试话术

**红线**：

1. **门禁是晋升唯一通道**：不过 G0–G6 + 发布审批不得 Published，禁止任何直发/旁路（对齐 01 红线 3）
2. **硬门无豁免**：违规率=0、泄漏=0、回归无倒退——不存在「先放后补」；质量类软门才有豁免通道
3. **阈值即代码**：阈值集版本化，线上手改阈值 = 绕过审计（等同改判不留笔录）
4. **豁免必须工单化**：有理由、有责任人、有期限，到期自动重拦——永久豁免等于没有这扇门
5. **判定必须留 gate_result**：verdict、实测值、阈值版本、签批方齐全——无留痕的通过不予承认
6. **抽检结论必须带统计依据**：样本量 + 分层 + 置信度，说不清楚的「抽检通过」不算通过

**面试话术（30 秒）**：

> "G0 到 G6 的检查项和阈值定义在生产域算子-02 那张 SSOT 表里，治理域做的是裁决面：门禁引擎拉各门实测、比对版本化阈值集、出 verdict，每次判定持久化成 gate_result 制品——过没过、差多少、依据哪个版本的阈值、谁签的，全部可回查。量刑分三级：G0/G1 是源头门，拦得越早越省 GPU；G2/G3 是软门，可回流修复重试；G4 违规、G5 泄漏、G6 回归倒退是硬门，全批拦截或回滚，没有豁免。阈值治理是判例法思路：阈值集自己版本化，改阈值走评审，例外放行必须工单加期限，到期自动重拦。还盯两个误判率——假阳误拦只是浪费算力，假阴漏放会污染下游，代价不对称，所以校准阈值时宁可严。这套和我做 XLB 配置治理完全同构：下发前合法性检查加变更审批，自动门规则签批、发布门人工签批，判定全留工单。"
