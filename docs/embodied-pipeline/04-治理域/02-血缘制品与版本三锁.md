## 1. 定位与边界

- **本篇管**：血缘图的**模型**（节点/边怎么定义）、**聚合**（样本级→版本级）、**查询**（正向溯源/反向影响面）、**完整性**（断链检测/对账）、**应用**（复现、Badcase 定位、影响面分析、泄漏审计）
- **不管**：单条记录怎么落（算子-04 §2）、版本制品字段（01 §4）、门禁怎么消费血缘结论（[03](03-质量门禁G0-G6.md)）
- **一句话**：算子-04 给的是「每样本一条账本记录」，本篇把账本聚成**一本可查的账**——账本记录是数据面的，账是治理面的

## 2. 核心概念与组件

| 组件 | 职责 | 要点 |
| --- | --- | --- |
| 血缘服务（Lineage Service） | 图的写入、聚合、查询 owner | 治理域组件（总线 §3④）；与数据文件分离存储 |
| 样本级血缘 | 每样本一条 produced_by 链 | 算子-04 §2 SSOT，执行时由算子写入 |
| lineage_graph | 版本级聚合图（DAG） | DatasetVersion 组成（01 §4 `lineage_graph_ref`） |
| 图存储 | 节点 + 边持久化 | 图库或关系库；数据迁冷存储时血缘不迁不删 |
| 查询 API | get_lineage / find_impact / trace_badcase | §6 |

> **与负载均衡治理同构**：血缘图 ≈ 配置变更审计链 + 依赖拓扑。回答「这次变更谁改的、改了什么、影响哪些下游 VIP」就是 blast radius 查询；回答「这条线上配置为什么长这样」就是正向溯源——血缘只是把被管对象从转发配置换成数据样本。

## 3. 血缘图模型（节点 / 边 / 聚合）

**节点类型（六类）**：数据集版本 / 样本 / 算子版本 / 模型版本 / 作业（管控域执行实例）/ Gate 结果（[03 gate_result](03-质量门禁G0-G6.md)）。

**边类型（三类语义）**：

| 边 | 方向 | 含义 |
| --- | --- | --- |
| `produced_by` | 数据 → 算子/作业 | 该数据由哪个算子版本（携模型版本）产出 |
| `derived` | 数据 → 数据 | 派生关系（版本演进、样本入集、切分产物） |
| `consumed_by` | 数据 → 训练作业 | 被哪次训练/评测消费（数据集为中心的另一半账） |

**两级聚合**：

```
样本级（算子-04 §2，每样本一条，执行时写入）
  s_0001 ─produced_by─ op-per-hand@1.2.0（model: hawor_cvpr25）
  s_0002 ─produced_by─ op-per-hand@1.2.0          ══聚合══►  lineage_graph(v3.1.0)
  s_0003 ─produced_by─ op-per-depth@1.0.0                    │
  s_000x ──derived── split=train（算子-07 §2）                ├ 节点：版本内全部样本/算子/模型/作业
                                                              ├ 边：produced_by + derived + split 标签
                                                              └ 出口：consumed_by → 训练作业 tr-042
```

- **聚合时机**：版本晋升时（Validated 前）把批次内全部样本血缘聚合为版本级图，登记进 DatasetVersion——01 §4 的 `lineage_graph_ref` 指向它
- **图随版本不可变**：Published 版本的 lineage_graph 只读；新版本 = 新图（差异部分复用父版本子图，对齐 01 §3 内容寻址的共享思路）

## 4. 两类核心查询

| 查询 | 方向 | 回答的问题 | 典型应用 |
| --- | --- | --- | --- |
| **正向溯源**（upstream） | 目标 ← 溯到源头 | 这条样本/版本**怎么来的** | 复现路径（三锁 + config_snapshot + hash → 重放，[管控域 04 声明式 reconcile](../03-管控域/04-PipelineSpec与编排DSL.md)）；GT 来源审计（[标注体系-02](../02-生产域/标注体系/02-标注质检与来源标记.md)） |
| **反向影响面**（blast radius） | 源头 → 波及面 | 某算子/模型/数据有缺陷，**波及谁** | 缺陷响应（哪些版本、哪些训练、哪些下游）、泄漏事件影响圈（[06 §6](06-数据分流与防泄漏.md)）、删除请求传播（[07 §6](07-合规引擎.md)） |

- **正向是复现的账**：拿到 lineage_graph 即可还原「哪个数据版本、过哪些算子版本、用什么模型版本、什么参数」——配合固定 seed 与确定性栈（算子-04 §3）支撑重放
- **反向是止损的账**：出事先圈影响面再动手修——顺序错了就是盲目重跑/盲目撤版

## 5. 血缘完整性与一致性

- **断链检测**：每个样本必须有完整 `produced_by` 链（从 RawDataPackage 入口到当前版本无缺环）；版本聚合前批量检测，断链样本进 Quarantined（[01 §5](01-版本管理与不可变快照.md)），补登记或显式废弃
- **血缘-manifest 对账**：图上样本集 = 版本 manifest 文件集（01 §4），不一致即告警（防「文件在图不在」或反之）
- **split 对账**：图的 split 标签与 [算子-07 §2](../02-生产域/算子设计/算子设计-07-四层数据集分流与防泄漏.md) 分流日志交叉核验——泄漏审计的血缘证据（[06 §4](06-数据分流与防泄漏.md)）
- **存储分离**：血缘存元数据服务（图库/关系库），与数据文件物理分离——数据可归档迁冷（资产域），**血缘与元数据不删**（01 §6 口径）

## 6. 查询 API 示意

```yaml
# 设计通识（接口形态与字段以实现为准）
get_lineage:                        # 正向溯源 / 反向遍历
  input:  {target: {kind: sample|dataset_version|operator|model,
                    id: s_0001 | v3.1.0 | op-per-hand@1.2.0},
           direction: upstream | downstream, depth: N}
  output: {nodes: [...], edges: [...],
           three_locks: {data_version, operator_version, model_version},
           config_snapshots: [...]}

find_impact:                        # 反向影响面（blast radius）
  input:  {source: {kind: operator|model|dataset, id: op-per-hand@1.2.0},
           scope: [published_versions, training_jobs, downstream_releases]}
  output: {affected_versions: [...], affected_trainings: [...],
           affected_samples: {count, sample_refs}}

trace_badcase:                      # Badcase 定位（回流闭环入口，总线 §6 #8）
  input:  {badcase_ref: sample_id, failure_class: transient|structural|resource|data}
  output: {path: [算子/模型版本链], suspect: {op_version, model_version},
           suggestion: rework | model_fix | recollect}
```

## 7. 指标与质量门

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| 血缘覆盖率 | 样本有完整 produced_by 链的比例 | **100%（硬要求，断链不发布）** |
| 血缘-manifest 对账一致率 | 图与文件清单一致 | 100% |
| 断链率 / 修复时长 | 断链样本占比与修复时效 | 趋势下降；断链批次不得晋升 |
| 查询时延 P95 | get_lineage / find_impact 响应 | 待标定（影响面查询是事件响应第一步，不能慢） |
| consumed_by 回写率 | 训练/评测消费登记比例 | 100%（没回写=消费侧账不全） |

## 9. 红线与面试话术

**红线**：

1. **先落账再发布**：不存在无血缘的样本——血缘登记与数据产出绑定，缺链版本禁止晋升（对齐 01 红线 4「三锁缺一不可」）
2. **血缘与数据文件分离存储**：数据可以归档迁冷，血缘与元数据永不删——账本跟着仓库走会一起丢
3. **血缘只追加不可改**：修正 = 追加新记录并标记 supersede，不抹历史（对齐 01 不可变语义与标注体系-02「不抹 qc_trace」口径）
4. **缺陷响应第一步是圈影响面**：先 find_impact 再动手——盲目重跑/撤版等于放大故障
5. **训练消费必须回写 consumed_by**：「哪个版本被哪次训练吃了」是数据集为中心账本的另一半，缺失则影响面永远查不全
6. **断链可修复但不可静默**：断链样本进 Quarantined 补登记或废弃，禁止带断链混过聚合

**面试话术（30 秒）**：

> "血缘我分两级做：算子层每样本一条 produced_by 记录，带三锁和 config_snapshot；治理层在版本晋升时聚合成版本级 lineage_graph，作为 DatasetVersion 的组成部分，节点六类、边三类——产出、派生、被训练消费。查询就两个方向：正向溯源回答『这条数据怎么来的』，凭三锁加配置快照可以完整重放；反向影响面回答『这个算子出 bug 波及谁』，先圈 blast radius 再止损。完整性上做断链检测和血缘-manifest 对账，断链样本进隔离区，缺链版本不许发布。这套和我在 XLB 做配置治理完全同构：变更审计链加依赖拓扑，正向查配置怎么来的、反向查变更影响哪些下游——被管对象从转发配置换成数据样本，账本逻辑一模一样。"
