## 1. 定位与边界

- **本篇管**：版本回归的**触发与判定**、回归**基线**的管理、**发布审批流**与发布物料、**回滚**执行、Golden Set 治理
- **不管**：门禁裁决与豁免（03）、评测指标与 GT（04）、版本号与内容寻址（01 §3）、泄漏检查内容（06）
- **一句话**：01 的状态机给出「Validated→Published 需要 G6+审批」，本篇回答**具体怎么走**——回归是考试，基线是及格线，审批是放行章，回滚是后悔药

## 2. 核心概念与组件

| 组件 | 职责 | 要点 |
| --- | --- | --- |
| 回归服务 | 触发/执行/判定 G6 回归 | 治理域「评测回归服务」（总线 §3④） |

> **与负载均衡治理同构**：这套就是**配置变更管理 + 灰度发布 + 版本回退**的移植——回归 = 变更前回归测试（防倒退才准入），基线 = 上一稳定版指标，发布门 = CAB 审批，回滚 = 切回稳定版本指针（蓝绿/版本回退），canary = 灰度小流量验证。我在 XLB 做的每次转发表变更都走这个流程，把被管对象换成数据集版本，一步不多一步不少。

## 3. 版本回归（触发 / 流程 / 判定）

**触发**：三锁任一变更（算子升级 / 模型替换 / 数据增删，算子-04 §3）——**没有「小改动免回归」**。

```
三锁变更 ──► 在 Golden Set 上跑全指标（L1–L3 全量；L4 按发布决策需要，04 §3）
                 │
                 ▼
        与基线对比（§4：含容忍度/显著性判定，防噪声抖动误判倒退）
                 │
        ├── 无倒退 ──► G6 verdict=pass（gate_result 留痕，03 §4）──► 发布审批流（§5）
        │
        └── 倒退 ────► G6 verdict=fail ──► 版本回滚（§6）/ 修复后重新回归
                                              （定位靠血缘 trace_badcase，02 §6）
```

- **考题固定**：Golden Set 是冻结的固定集（算子-07 §5）——考题变了的考试没有可比性
- **指标全面**：回归跑的不只是变更算子的指标，是该算子**下游全链路**受影响指标（数据是流下去的，算子-04 §1「数据增删→影响下游评测」）

## 4. 回归基线管理

- **基线记什么**：每算子/每层质量指标的历史基准值（来自历次 EvaluationReport，04 §6），存基线注册表
- **基线怎么更新**：基线版本**随 Golden Set 受控更新**——Golden Set 扩充走评审 + 全量重基准（算子-07 §5），基线必须用同一版本考题重算，**禁止顺手改基线**
- **对比判定**：实测 vs 基线要给**容忍度或显著性判定**（固定容忍带 / 统计检验，二选一，设计通识待定）——指标在噪声带宽内的抖动不算倒退；把噪声当倒退 = 回归疲劳，把倒退当噪声 = 放水
- **基线与豁免的边界**：指标略降但业务可接受 → 走 03 §6 豁免工单（有期限），**不是**改基线——豁免是「这次例外」，改基线是「以后都行」，性质完全不同

## 5. 发布审批流与发布物料

```
Validated ──► G6 回归 pass ──► 发布检查清单 ──► 审批（自动门 + 人工发布门）──► Published
（01 §5）                          │ 不满足/驳回            │
                                  ▼                        ▼
                           修复后重新进入             change record 留痕
                           （状态机不变：仍在 Validated）
```

- **发布检查清单**（全过才进审批）：三锁齐（01 红线 4）/ 泄漏=0（[06](06-数据分流与防泄漏.md)）/ 违规=0（[07](07-合规引擎.md)）/ 评测达标（[04 报告](04-四层评测体系L1-L4.md)）/ 回滚预案在（§6）
- **审批两级**：自动门 = 规则签批（清单机器核对，03 §3 签批分工）；**人工发布门 = 发布责任人签批，不可省**——自动门核对事实，人工门承担发布决策责任
- **发布物料**（缺一不发）：`DatasetVersion` 晋升令牌（01）/ release notes（版本 diff：文件增删改 + 三锁变化 + 指标变化，01 §6）/ EvaluationReport（04）/ 下游兼容说明（schema 版本、破坏性变更提示）
- **发布是受控变更（change record）**：谁、何时、批了什么版本、依据哪些 gate_result——发布记录本身就是审计对象

## 6. 回滚

- **触发**：发布后发现质量倒退 / 缺陷 / 泄漏事件（[06 §6](06-数据分流与防泄漏.md) 响应流程）
- **执行**：当前版本标 Deprecated，**默认版本指针切回上一稳定版**（01 §6）——指针切换、秒级生效、不删历史
- **之后**：问题定位（血缘 blast radius，02 §4）→ 修复走**新版本**重新过 G6 + 审批——回滚是止血，不是治疗；治疗永远走新版本
- **回滚次数是发布质量的反向指标**（01 §7）：回滚多 = 回归判定或审批在放水

## 7. Golden Set 管理（治理面）

- **固定版本、防过拟合**：长期不变（算子-07 §5）——对考题过拟合的模型会在真实考场露馅，对 Golden 过拟合的版本会在下游露馅
- **受控扩充**：确需扩充 → 评审 → **全量重基准**（新 Golden 上重跑全部基线，§4）——考题变了必须重新划及格线
- **防泄漏双向红线**：Golden 不进训练（[06 §5](06-数据分流与防泄漏.md)）；新增训练数据与 Golden 做泄漏抽检（G6，算子-07 §4）
- **灰度 / canary（可选通识，待产品决策）**：新版本先小比例下游验证（部分训练任务引用新版）→ 无异常再全面切默认指针——与 LB 灰度发布同构；数据集场景下「小流量」= 少量训练任务先行

## 8. 指标与质量门

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| 回归触发率 | 三锁变更实际触发回归的比例 | **100%（无免回归通道）** |
| 回归时长 | 触发到 G6 verdict | ≤24h（总线附录 A 示例值，待标定） |
| 回归通过率 / 修复后二次通过率 | 一次过 / 修复后再过 | 二次通过率高说明回归拦得准、修得动 |
| 发布周期 | 两次 Published 间隔 | 待标定（节奏指标，不是越快越好） |
| 回滚次数 / 回滚时长 | 01 §7 已定义 | 次数趋零；时长秒级（切指针） |
| 审批时效 | 提交审批到签批 | 待标定（人工门是时效瓶颈，要监控不放水） |

## 10. 红线与速讲话术

**红线**：

1. **三锁任一变更必须回归**：没有「小改动免回归」——数据集上没有小改动，样本级变更会流到下游全链路
2. **基线不许顺手改**：基线只随 Golden Set 受控更新 + 全量重基准；想让倒退消失的正确姿势是豁免工单（03 §6），不是改及格线
3. **人工发布门不可省**：自动门核对事实，人工门承担发布责任——全自动发布等于无人对发布负责
4. **发布物料缺一不发**：三锁、报告、release notes、兼容说明——下游拿着不完整的物料没法做兼容决策
5. **回滚切指针不删历史**（01 §6）：修复永远走新版本重新过 G6——在 Published 版本上打补丁 = 破坏不可变
6. **Golden Set 防过拟合**：受控扩充 + 全量重基准，考题管理比考分管理更重要

**速讲话术（30 秒）**：

> "版本发布的路径是：三锁任一变更就在 Golden Set 上跑全指标回归，和基线对比给容忍度判定，防噪声抖动误判倒退；无倒退过 G6，再走发布检查清单——三锁齐、泄漏零、违规零、评测达标、回滚预案在——然后自动门加人工发布门双签批，才 Published。基线管理是关键：基线只随 Golden Set 受控更新、全量重基准，禁止为了放过版本顺手改基线，业务可接受的例外走豁免工单、有期限。回滚是切默认版本指针，秒级止血不删历史，修复走新版本重新过 G6。这套就是我做 XLB 配置变更的完整搬运：变更前回归测试、CAB 审批、灰度验证、版本回退——治理对象从转发表换成数据集，发布纪律一模一样。"
