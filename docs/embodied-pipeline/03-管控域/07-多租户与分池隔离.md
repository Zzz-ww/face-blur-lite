# 07 · 多租户与分池隔离（namespace / ResourceQuota / 队列树 / 三池互不挤兑）

> 03-管控域第 7 篇，拆自 [02-调度与多租户](02-调度与多租户.md) §4.3 深化。定位：**谁能用多少资源**——租户怎么隔离、配额树怎么挂、三大池怎么互不挤兑、怎么防配额绕过。边界：调度链与准入在 [02](02-调度与多租户.md)、优先级与抢占在 [06](06-优先级抢占与公平性.md)；计量账单在 [横切 03](../90-横切/03-多租户与计量计费.md)；合规规则侧在 [治理 07](../04-治理域/07-合规引擎.md)；本篇只讲隔离模型、配额树层级、分池口径与隔离审计。

## 核实状态（2026-10-19）

- ✅ 已核实：namespace 隔离 + ResourceQuota 硬顶 = K8s 原生机制；Kueue ClusterQueue/Cohort 与 nominalQuota 保底 + borrowing 借用为官方文档化机制（对象字段随版本演进有差异，以部署版本为准，同 [02 篇核实状态](02-调度与多租户.md)）；ElasticQuotaTree 为阿里等业界层级弹性配额理念（保底+借用+回收），非 K8s 原生对象名（02 §4.2）；三池口径「数据平台 / 训练 / 评测互不挤兑」与 [总线 §3③](../00-总体架构/README.md)、[算子设计-03 §6](../02-生产域/算子设计/算子设计-03-算子执行与编排规范.md) 一致；隔离合规审计口径以 [治理 07 §8](../04-治理域/07-合规引擎.md) 为准
- ⚠️ 设计通识：一租户一 namespace 一 LocalQueue 一 ClusterQueue 的映射、三池的 ClusterQueue/ResourceFlavor 落法、池间配额比例为本平台设计（以团队标定为准）
- ❓ 待补：各池配额基线与借用比例、跨池挤兑事件告警阈值、租户配额使用率报表节奏——待团队标定

## 1. 定位与边界

- **本篇管**：**隔离模型**（租户怎么映射、硬顶怎么兜底）、**队列树与配额树**（LocalQueue → ClusterQueue → Cohort 怎么挂）、**三池分池口径**（互不挤兑怎么落地、借用边界在哪）、**隔离审计与计量联动**
- **不管**：准不准入、池内排队序与抢占（02/06）、计量四类口径与账单（横切 03）、合规规则怎么定义（治理 07）
- **一句话**：隔离决定「你崩了不连累我」，配额决定「你能用多少」，分池决定「关键池不被挤兑」——三件事一套体系（namespace + 两层配额 + 池级队列树）

## 2. 隔离模型（namespace 硬隔离 + 两层配额各司其职）

| 组件 | 归属层 | 职责 |
| --- | --- | --- |
| namespace | K8s 原生 | 租户资源对象边界：CR/Pod/Secret 全部落租户 namespace |
| ResourceQuota | K8s 原生 | 硬顶兜底：namespace 内资源总量上限——碎了也不许超 |
| LocalQueue | Kueue | 租户作业入口（一租户一个，映射到自己的 ClusterQueue） |
| ClusterQueue + Cohort | Kueue | 配额主体（nominalQuota 保底 + 借用）与组内共享池 |

- **namespace 硬隔离**：一租户一 namespace——资源对象边界天然隔离；RBAC 授权（[横切 02](../90-横切/02-安全合规.md)，角色底表在[总线附录 C](../00-总体架构/README.md)）与审计都以 namespace 为锚，租户的任何对象不落自己的 namespace 就是隔离违规（§5 审计项）
- **两层配额各司其职**（02 §4.3 口径展开）：

| 层 | 性质 | 回答的问题 |
| --- | --- | --- |
| ResourceQuota | 硬顶（K8s 原生强制） | 配额体系全失效时，namespace 最多吃多少——**最后防线** |
| ClusterQueue | 弹性（nominalQuota + borrowingLimit） | 正常运行时能保底多少、最多借多少——**利用率优先** |

只留硬顶 = 碎片化闲置；只留弹性 = 失去兜底（02 红线 2：双层缺一不可）
- **租户映射**：一租户一 namespace 一 LocalQueue 一 ClusterQueue，配额树挂 Cohort——**租户的配额身份唯一**，计量、审计、账单都有唯一锚点（串账排查从 namespace 一步定位，[横切 03 §6](../90-横切/03-多租户与计量计费.md) 计量隔离）

> **与负载均衡/控制面同构**：多租户隔离 ≈ 转发面多租户配置空间隔离（一租户一配置域，互不可见互不可写）；ResourceQuota 硬顶 ≈ 单板资源的硬限速——软共享之上永远留一道硬限；配额 ≈ 转发资源限流，共享提利用率、限流保下限——**隔离与共享的配比问题**在哪个控制面都长一样。

## 3. 队列树与配额树（重点节）

```
namespace（租户边界，K8s 原生）
  └─ LocalQueue（作业入口：管「谁提交」）
        └─ ClusterQueue（配额主体：nominalQuota 保底 + borrowingLimit 上限）
              └─ Cohort（组内共享池：管「能不能借」）
                    ├─ dsp 池    数据平台（生产管线）
                    ├─ train 池  训练
                    └─ eval 池   评测
```

- **三级各司其职**：入口（LocalQueue）管提交归属，配额（ClusterQueue）管资源边界，组（Cohort）管跨队列弹性——跳过任何一级（比如直接向 ClusterQueue 提交）都会让租户身份或配额边界失锚
- **nominalQuota 保底 + borrowing 借用规则**（02 §4.2 展开）：
  - **保底**：nominalQuota 是主人的下限——组内任何人借用都不影响主人保底可用
  - **借用**：组内空闲份额可借（borrowingLimit 封顶），借用按需
  - **回收**：`ReclaimNominalQuota`——主人需要保底份额时收回借出份额，回收触发组内抢占、被回收方走 Evicted → Queued（抢占执行与护栏见 [06 §3](06-优先级抢占与公平性.md)；02 §5.2 口径）
  - **层级弹性 = ElasticQuotaTree 理念**：父队列挂子队列、保底+借用+回收；在 Kueue 语境由 ClusterQueue + Cohort 组合实现——**理念对齐，对象名不混用**（02 §4.2）
- **配额维度**：GPU 为核心 + CPU/内存（02 §4.1 resourceGroups 同款）——只配 GPU 不配 CPU 的队列会被 CPU 大户反噬；公平侧同一道理见 [06 §4](06-优先级抢占与公平性.md)（配额维度集合 = 公平性维度集合）

## 4. 三池分池口径（重点节）

- **口径**（[总线 §3③](../00-总体架构/README.md)、[算子-03 §6](../02-生产域/算子设计/算子设计-03-算子执行与编排规范.md)）：数据平台 / 训练 / 评测三大池**互不挤兑**——评测高峰不允许吃掉生产配额，反之亦然；跨池挤兑事件数是审计项，**应恒为 0**（02 红线 6）
- **为什么评测池最危险**：评测是脉冲负载（发版前集中跑 L4），天然倾向在高峰期把能借的都借了——不分池的话，每次发版评测潮都会把生产批挤成 Evicted 循环；分池把「脉冲」关在自己的池子里
- **分池实现（两层）**：

| 层 | 落法 | 管什么 |
| --- | --- | --- |
| namespace/ClusterQueue 级 | 池 = 独立 namespace + 独立 ClusterQueue（可挂同一 Cohort 受控借用） | 池间总量隔离 |
| ResourceFlavor 级 | 型号细分（gpu-a100 / gpu-l40 …，02 §6 示例） | 型号错配——A100 的活别落 L40；细化归 [08](08-GPU资源池与弹性.md) |

- **池间借用的红线**：**临时借用可、长期挤占不可**——「评测常年借生产」= 结构性挤兑，不是弹性；审计看**借用份额滞留时长**（02 §7）而非借用次数（借了还得起、还得出，ReclaimNominalQuota 兜底）——滞留时长超阈值就是挤兑信号，不是利用率高的信号

## 5. 租户隔离审计与计量联动

- **隔离合规审计项**（挂 [治理 07 §8](../04-治理域/07-合规引擎.md) 审计框架，规则侧 SSOT 在治理域）：

| 审计项 | 查什么 | 违规信号 |
| --- | --- | --- |
| namespace 边界完整性 | 租户资源对象是否全落自己 namespace | namespace 外出现租户作业对象 |
| 跨 namespace 访问清单 | 谁跨 namespace 访问了什么 | 未审批的跨池/跨租户访问 |
| ResourceQuota 兜底未绕过 | 硬顶命中与绕过尝试 | 直接建 Pod 绕过准入（与 02 红线 1 同源） |

- **配额 → 计量联动**（账房闭环，[横切 03 §6](../90-横切/03-多租户与计量计费.md)）：
  - ClusterQueue nominalQuota = 预算的配额落点——**预算 → 配额 → 用量 → 账单四环**（[横切 03 §5](../90-横切/03-多租户与计量计费.md)），配额不是平台送的，是预算换的
  - 配额使用量 → 计量记录（算力类用量，横切 03 §4）→ 项目账单；**配额调整必走审批留审计痕**
  - 计量隔离：一个项目的成本绝不许算到另一个头上——**串账即 P0**（横切 03 §6）
- **审计输出**：每租户配额使用率报表（nominal vs borrowed 占比）、违规清单（挤兑/绕过/越权）——喂 [横切 01](../90-横切/01-可观测性.md) 告警与治理域合规报告

## 6. 指标与质量门

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| 池利用率 | 各池 nominal 使用占比 | 容量规划：该扩池还是收配额（联动横切 03 §5 预算复盘） |
| 跨池挤兑事件数 | 评测/生产互相挤占事件 | **应恒为 0（红线）** |
| ResourceQuota 兜底命中次数 | 硬顶拦截次数 | = 配额体系被绕过的尝试数——非 0 即查 |
| 配额命中率 | 作业申请即被准入比例 | 弹性模型好不好用（借用是否真的在发生） |
| 隔离违规数 / 审计覆盖率 | §5 审计项违规数与覆盖比例 | 违规清零、覆盖率 **100%** |

## 8. 红线与速讲话术

**红线**：

1. **硬顶不可绕过**：ResourceQuota 兜底是最后防线——配额体系被绕过即安全事件（与 02 红线 1「不许绕过 Kueue 直接建 Pod」同源，双层都要守）
2. **三池互不挤兑是审计项**：数据平台/训练/评测跨池长期挤占 = 违规——评测高峰吃掉生产配额即事故（恒 0 指标）
3. **借用有度**：长期占 borrowed 把主人挤成二等公民 = 公平破坏——借了要还得起（ReclaimNominalQuota），审计看滞留时长不看借用次数
4. **配额是上限不是承诺**：nominalQuota 保底也要在池内排队——保底是下限可用性，不是预留占位
5. **隔离审计不可豁免**：租户资源边界必须有审计记录——无审计的隔离 = 自称隔离
6. **GPU 型号分池与配额脱钩即 OOM 风险**：型号错配不属配额问题（配额只管数量不管型号）——型号约束归 [08](08-GPU资源池与弹性.md) 的 ResourceFlavor/拓扑层，配额层不许替它兜底

**速讲话术（30 秒）**：

> "多租户我按三层讲：namespace 硬隔离给租户资源对象边界，ResourceQuota 硬顶做最后防线——Kueue 配额体系全被打穿时 namespace 也吃不多；中间层是 ClusterQueue 弹性配额，nominalQuota 保底加借用上限，一租户一 namespace 一 LocalQueue 一 ClusterQueue，配额身份唯一，计量审计账单都有唯一锚点。配额树挂 Cohort：空闲即借、主人 ReclaimNominalQuota 回收保底，对应阿里 ElasticQuotaTree 的层级弹性理念。三池分池是审计项：数据平台、训练、评测互不挤兑——评测是脉冲负载，不分池每次发版评测潮都把生产批挤成驱逐循环；池间借用临时可以、长期挤占不行，审计看借用滞留时长不看次数。审计三项：namespace 边界完整性、跨 namespace 访问清单、硬顶绕过尝试；计量联动是预算到配额到用量到账单四环，串账即 P0。这套就是 XLB 多租户的搬运：配置空间隔离、转发资源限流、关键业务 QoS 不被批量业务挤占、流量账单——被管对象从带宽换成 GPU，隔离与共享的配比逻辑一字不改。"
