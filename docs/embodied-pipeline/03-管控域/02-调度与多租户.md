# 02 · 调度与多租户（四级调度链 / Kueue 配额准入 / 优先级抢占 / 公平性）

## 1. 定位与边界

- **本篇管**：作业**进不进、什么时候进、进了用谁的资源**——准入（Admission）、配额（Quota）、优先级与抢占（Priority/Preemption）、公平（Fairness）、多租户隔离（Multi-tenancy）
- **不管**：Pod 落到哪个节点（kube-scheduler）、集群怎么起（01 篇）、任务在 Ray 集群内怎么放置（Ray 两级调度）、作业失败后怎么办（03 篇）
- **一句话定位**：本篇是整个平台的**资源闸门**——所有 GPU 花销从这里放行，成本（[算子设计-06](../02-生产域/算子设计/算子设计-06-算子成本模型.md)）与优先级治理在这里生效

## 2. 核心概念与组件

| 组件 | 归属层 | 职责 |
| --- | --- | --- |
| kube-scheduler | K8s 原生 | 把**已创建**的 Pod 绑定到节点（资源余量/亲和/污点/拓扑） |
| Kueue | K8s 准入层 | 作业在 Pod 创建**前**作为 Workload 排队，按配额/优先级决定**准不准入、何时准入** |
| KubeRay operator | K8s 编排层 | 准入放行后按 CR 起 head/worker Pod（[01 篇 §3](01-KubeRay控制面.md)） |
| Ray 调度器 | 集群内任务层 | 两级调度（Local→Global）把 Actor/Task 放到 worker 节点（调研笔记-02 §1.2） |
| ResourceFlavor / ClusterQueue / LocalQueue / Cohort / Workload | Kueue 对象 | 资源风味 / 配额主体 / 租户入口 / 队列组 / 排队单元（§4，通识） |
| PriorityClass | K8s 原生 | Pod/作业优先级，抢占依据 |

> **与负载均衡控制面同构**：Kueue 准入层 ≈ LB 的连接准入与限流闸门（过载保护在后、转发面在前）；配额 ≈ 容量规划；「准入在前、执行在后、各层不越权」的分层与 XLB 完全同构。

## 3. 控制面机制：四级调度链（谁先谁后、各看什么）

```
用户提交 PipelineSpec（[04 篇](04-PipelineSpec与编排DSL.md) DSL）
        │  编译为 RayJob / RayCluster CR + Workload 申请
        ▼
【L1 准入层 · Kueue】（Pod 创建之前）──────────────────────────────
   看什么：配额（nominalQuota / borrowingLimit）、优先级、Cohort 借用
   做什么：决定「准不准入、何时准入」；准入 = 资源预留（Admission）
   不做什么：不决定 Pod 落哪个节点——那是 kube-scheduler 的事
        │  准入放行 → 允许创建 Pod
        ▼
【L2 编排层 · KubeRay】（01 篇）──────────────────────────────────
   operator reconcile：按 CR 期望态起 head / worker Pod
        │  Pod 进入调度队列
        ▼
【L3 节点层 · kube-scheduler】（K8s 原生）────────────────────────
   看什么：节点资源余量、亲和/反亲和、污点容忍、GPU 拓扑
   做什么：把已创建的 Pod 绑定（bind）到具体节点
        │  Pod Running、节点加入 Ray 集群
        ▼
【L4 任务层 · Ray 调度器】（集群内）──────────────────────────────
   两级调度：Local Scheduler 就近执行，不行交 Global（调研笔记-02 §1.2）
   看什么：Actor/Task 的 num_gpus/num_cpus 逻辑资源请求
   做什么：把算子任务放到 worker 节点执行（L2 分片即在此落地）
```

三条最容易讲错的边界：

- **Kueue 不替代 kube-scheduler**：它管的是作业准入与配额闸门，在 Pod 创建前生效；节点绑定仍是 kube-scheduler 的职责
- **Kueue 也不替代 Ray autoscaler**：配额卡的是「总共能起多少 Pod」（L1/L2/L3 层面）；集群内部「这批任务需要几个 worker」是 Ray 逻辑资源视图（[01 篇 §5](01-KubeRay控制面.md) 三层伸缩）
- **四级是时序链不是管理层级**：L1 过了才有 L2 的 Pod 创建，L2 创建了才有 L3 的节点绑定，L3 绑定了 L4 才有可放置的 worker——上层不越权替下层做决定

## 4. 配额与准入模型（Kueue 对象 + ElasticQuotaTree）

### 4.1 Kueue 关键对象（通识，字段以版本为准）

| 对象 | 作用域 | 职责 |
| --- | --- | --- |
| ResourceFlavor | 集群 | 资源风味：关联节点标签/污点（如 `gpu-a100` / `gpu-l40`），配额按风味声明——**GPU 型号分池的落点** |
| ClusterQueue | 集群 | 配额主体：`nominalQuota` 名义配额（保底）+ `borrowingLimit` 借用上限（弹性）；准入决策者 |
| LocalQueue | 命名空间 | 租户入口：作业提交指向的队列，映射到 ClusterQueue |
| Cohort | 集群 | 队列组：组内队列可共享/借用配额（空闲即借、回收有度） |
| Workload | 集群 | 排队单元：一个作业的资源申请快照（podSet）；被准入/抢占/驱逐都作用于它 |

### 4.2 ElasticQuotaTree：层级弹性配额理念

- 阿里等业界的**层级配额**实践：父队列下挂子队列，每个子队列有 guaranteed（保底）与 borrowed（借用）两层；**高优回收**——配额主人需要时收回被借走的份额
- 与 Kueue 的对齐：Cohort 提供「组内共享/借用」，层级配额靠 ClusterQueue+Cohort 组合出树；总线 §3③ 写的「Kueue 调度器（ElasticQuotaTree）」即此对应关系——**理念对齐，对象名不混用**（ElasticQuotaTree 非 K8s 原生）
- 数据平台落地形态（通识）：顶层分「数据平台 / 训练 / 评测」三大池，池内按阶段（L2 感知 / L3 语义 / 回归）分子队列；空闲池可被借用，但 Golden Set 回归到来时按优先级回收

### 4.3 多租户分池与隔离

- **namespace 隔离 + ResourceQuota 硬顶**（K8s 原生）：兜底安全线，防配额体系被绕过后打爆命名空间
- **两层配额各司其职**：ResourceQuota = 硬顶（碎了也不许超）；ClusterQueue = 弹性（nominalQuota 保底 + 借用）——只留硬顶会碎片化闲置，只留弹性会失去兜底
- **分池口径**（总线 §3③）：数据平台 / 训练 / 评测三大池互不挤兑——评测高峰不允许吃掉生产配额，反之亦然
- **GPU 维度**：按型号/显存分 ResourceFlavor + worker 组（01 篇 §4.1）；拓扑感知（NVLink/网络亲和）为进阶优化（通识，待标定收益）
- **BinPacking vs Spread**：BinPacking 装满再开新节点（利缩容、省成本）；Spread 打散（利容错、防同节点故障一锅端）——批处理默认 BinPacking，常驻关键池偏 Spread（通识取舍）

### 4.4 数据局部性（说明即可）

管线数据主存在对象存储（OSS/S3），worker 经网络拉取（[算子设计-03 §9](../02-生产域/算子设计/算子设计-03-算子执行与编排规范.md)）——**数据局部性不是主要矛盾**，调度优先级序 = GPU 型号池匹配 > 配额/优先级 > 网络/拓扑；这与 ML 训练集群「数据本地盘亲和」是不同场景，不需要照搬其局部性调度。

## 5. Gang 调度、优先级与公平

### 5.1 Gang scheduling（AllOrNothing）

- **为什么**：多 worker 作业若「部分起、占着资源等其余」，会死锁/资源占死——所有 worker 必须同时准入，要么都别进
- **Kueue 的现实（通识口径）**：通常靠 `waitForPodsReady`（Pods 不全 ready 则挂起/重排队，不让半成品占位）+ coscheduling plugin（scheduler-plugins）或外部批调度器（Volcano 等）组合实现——**不能写成「Kueue 原生就完整支持 gang」**
- **Ray 场景的辨析**：Ray 集群天然允许 worker 渐进加入（autoscaler 语义，head 先起、worker 陆续到位），所以**gang 的刚性需求集中在分布式训练类作业**（Ray Train 多卡同步，缺一卡全队等）；数据管线批处理（RayJob + 常驻池）对 gang 依赖弱——这是本平台「管线松、训练严」的分级依据

### 5.2 优先级与抢占

- **优先级来源**：K8s PriorityClass → Workload priority；队列优先级（LocalQueue/ClusterQueue 级）
- **高优示例**（算子设计-03 §5 同口径）：Golden Set 回归（G6 触发，SLO 24h 内完成）、线上 badcase 修复——可插队，必要时抢占低优
- **抢占策略**（通识，策略名以版本为准）：`withinClusterQueue`（同队列内抢）、`withinCohort`（组内跨队列借出份额可收回）、`ReclaimNominalQuota`（配额主人回收自己的保底份额）
- **被抢占方语义**：作业进入 `Evicted` → 释放资源 → 重回 Queued（保留检查点续跑，不从头来）——状态推进归 [03 篇](03-任务状态机与容错.md)
- **spot 实例回收**同通道：节点被云回收 = 外部驱动的「被抢占」，走 Evicted→重新排队（配 [01 篇 §6](01-KubeRay控制面.md) worker 重建）

### 5.3 公平性

- **多资源维度**：GPU+CPU+内存同时看——DRF（主导资源公平）：每个租户的主导资源份额对齐才叫公平；单维度 max-min 会被「GPU 大户 CPU 也大户」的租户钻空子
- **cohort 内公平借用**：借用按需、回收有度（§4.2）；防止某队列长期占着 borrowed 份额把主人挤成二等公民
- **防饥饿**：低优先级作业靠年龄加权/最小份额兜底（通识；具体策略待团队标定）

## 6. 关键字段示例（Kueue 对象，通识）

```yaml
# 字段名以部署版本为准（示意）
apiVersion: kueue.x-k8s.io/v1beta1
kind: ResourceFlavor            # GPU 型号 → 节点标签（分池落点）
metadata: {name: gpu-a100}
spec:
  nodeLabels: {node.kubernetes.io/instance-type: gpu-a100-80g}
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: ClusterQueue              # 配额主体：保底 + 借用上限
metadata: {name: dsp-l2-cq}
spec:
  namespaceSelector:
    matchLabels: {tenant-tier: data-platform}   # 按 namespace 标签纳入本队列（标准 label selector）
  cohort: dsp-cohort            # 组内可共享/借用（§4.2 层级配额的组）
  resourceGroups:
    - flavors: [{name: gpu-a100}]
      resources:
        - {name: nvidia.com/gpu, nominalQuota: 16, borrowingLimit: 8}
        - {name: cpu,           nominalQuota: 256, borrowingLimit: 128}
---
apiVersion: kueue.x-k8s.io/v1beta1
kind: LocalQueue                # 租户入口：作业提交指向这里
metadata: {name: l2-perception-lq, namespace: data-platform}
spec: {clusterQueue: dsp-l2-cq}
```

读法：L2 感知作业提交到 `l2-perception-lq` → 进 `dsp-l2-cq` 排队 → 名义配额 16 卡保底、最多借 8 卡 → 空闲时从 cohort 借、主人（Golden 回归队列）要用时被回收。

## 7. 指标与质量门（L2/L3 落点）

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| 准入等待时长（P50/P95） | 提交到 Admitted 的排队时间 | L3 队列延迟主指标；SLO 输入 |
| 排队深度 / 准入率 | 各 LocalQueue 积压与放行比例 | 容量规划信号（该扩池还是该加配额） |
| 配额利用率 | nominal vs borrowed 使用占比 | 评估超卖安全度；成本联动（[算子设计-06](../02-生产域/算子设计/算子设计-06-算子成本模型.md)） |
| 抢占次数 / 被抢恢复时长 | Evicted 发生频率与恢复耗时 | 抢占护栏是否过紧/过松 |
| 借用份额滞留时长 | borrowed 被占用时长分布 | 公平性审计（§5.3） |
| 分池隔离审计 | 三大池互相挤兑事件数 | 应恒为 0（红线） |

> 数据面指标（样本/小时、算子 P50–P99、GPU 秒/样本）归 [算子设计-03 §10](../02-生产域/算子设计/算子设计-03-算子执行与编排规范.md)；本篇只采集「**闸门开得好不好**」。队列延迟直接进入端到端 L2 端到端成功率的时延预算。

## 9. 红线与面试话术

**红线**：

1. **不许绕过 Kueue 直接建 Pod**：任何绕过准入层的资源申请 = 配额旁路，分池隔离与成本核算全部失真；新执行形态必须先接 Workload 准入
2. **配额双层缺一不可**：ResourceQuota 硬顶（安全兜底）+ ClusterQueue 弹性（保底+借用）——只有硬顶碎片化闲置，只有弹性失去兜底
3. **训练类作业必须 gang（AllOrNothing）**：靠 `waitForPodsReady` + coscheduling/批调度器组合实现，不假设 Kueue 原生完整支持；管线批处理可放宽（Ray autoscaler 渐进语义）
4. **抢占有护栏**：只抢「可从检查点恢复」的批处理作业；Golden/发布类作业不得作为被抢客体——被抢必须能续跑（[03 篇](03-任务状态机与容错.md)），否则禁止抢占
5. **名义配额是保底不是目标**：常态借用（超卖）要留资源争抢余量，borrowingLimit 是防雪崩的上限，不是常态水位
6. **三池互不挤兑是审计项**：数据平台/训练/评测互相挤兑事件数应恒为 0——评测高峰吃掉生产配额即事故

**面试话术（30 秒）**：

> "调度我按四级链讲：作业先过 Kueue 准入层——在 Pod 创建之前，按 ClusterQueue 的名义配额加借用上限、优先级和 Cohort 共享决定准不准入；放行后 KubeRay 起集群，kube-scheduler 把 Pod 绑到节点，最后 Ray 内部两级调度把 Actor 放到 worker。关键是不越权：Kueue 不替代 kube-scheduler，它管的是配额闸门不是节点选择。配额模型是保底加弹性：nominalQuota 保底、cohort 内借用、配额主人可回收，对应阿里的 ElasticQuotaTree 层级配额理念。多租户三层隔离：namespace 加 ResourceQuota 硬顶兜底，数据平台/训练/评测分池互不挤兑。训练类作业必须 gang 调度 AllOrNothing，用 waitForPodsReady 加 coscheduling 组合实现。这和我在 XLB 做的准入控制同构——限流闸门在转发面之前，各层只做自己的决定。"
