## 1. 设计目标与原则

**目标**：一个平台覆盖"采集 → 生产 → 治理 → 资产 → 消费"全链路，让数据从原始信号变成可直接训练、可审计、可迭代的数据集资产。

**设计原则（业内通识）**：

1. **面分离**：控制面（编排/调度/状态）与数据面（算子执行）分离——各自独立演进，接口只通过声明式规格交互
2. **数据集为中心**：一切域围绕"数据集资产"运转——作业吃数据集、产数据集，治理管数据集，消费读数据集
3. **声明式 + 不可变**：期望状态声明，控制循环收敛；数据集版本一经发布不可变（可精确复现）
4. **可追溯**：血缘制品化贯穿全链路（这条样本怎么来的、被哪次训练用过）
5. **门禁驱动发布**：质量门禁（规则→互检→抽检→回归）是数据集版本晋升的唯一通道
6. **渐进演进**：MVP 先通链路，控制面/治理后补强，规模化再上多租户与计量

## 2. 总体架构：一个入口 + 六大域 + 三层横切

```
┌────────────────────────────────────────────────────┐
│  用户入口层：Web 控制台 · CLI · SDK · API 网关        │
├────────────────────────────────────────────────────┤
│  ① 接入域    采集工厂（多源接入/设备/上云/校验）      │
│  ② 生产域    数据面（算子流水线：预处理/感知/语义/清洗/脱敏/封装）│
│  ③ 管控域    控制面（编排/调度/状态/资源/多租户）     │
│  ④ 治理域    版本/血缘/门禁/合规/评测回归            │
│  ⑤ 资产域    数据集资产（湖仓/检索/快照/目录）        │
│  ⑥ 消费域    训练/评测/回流                         │
├────────────────────────────────────────────────────┤
│  横切：可观测性 · 安全合规 · 多租户与计量             │
└────────────────────────────────────────────────────┘
```

## 3. 六大域详设（职责 / 关键组件 / 接口）

### ① 接入域（采集工厂）

- **职责**：多源数据接入（真机遥操作、第一视角、仿真、动捕、rosbag）、设备/机器人管理、数据上云、源头完整性校验
- **组件**：采集 Agent/客户端、设备管理服务、数据接入网关、原始数据湖（对象存储）
- **接口**：原始数据包 + schema 元数据（接入即校验，不合格源头拦截）
- **业内参照**：智域基石式真机采集工厂（异构硬件统一接入）；华为云 CloudRobo 多本体接入

### ② 生产域（数据面 · 算子流水线）

- **职责**：执行算子全集——预处理（帧规范化）、感知结构化（检测/重建/深度/位姿）、语义标注（VLM）、清洗质检、脱敏合规、格式封装（LeRobot v2/v3 / RLDS）
- **组件**：算子库（Data-Juicer 式）、算子引擎（CPU Ray Data / GPU Actor / RayJob / RayService）、算子 DAG 执行器
- **接口**：输入数据集 + PipelineSpec（DAG）→ 输出数据集 + 质检报告
- **业内参照**：阿里云 PAI Data-Juicer VLA 流水线（算子级拆解见 [算子设计-01](算子设计/算子设计-01-业内通用算子全集总览.md)）

### ③ 管控域（控制面）

- **职责**：任务编排（DAG/重试/断点续跑）、调度（队列/配额/优先级/gang scheduling）、状态机与生命周期、资源管理、多租户分池
- **组件**：KubeRay（RayCluster/RayJob/RayService CRD）、Kueue 调度器（ElasticQuotaTree）、状态存储（etcd/元数据库）、任务管理服务
- **接口**：声明式 PipelineSpec → 作业生命周期状态
- **业内参照**：KubeRay + Kueue 跨团队调度（阿里云 ACK 验证；细节见 [调研笔记-02](调研笔记/调研笔记-02-Ray分布式框架调研与管线应用.md)）

### ④ 治理域

- **职责**：数据集版本管理（不可变快照）、血缘追踪（制品化）、质量门禁（规则→互检→抽检→Golden Set 回归→发布审批）、合规引擎、评测回归
- **组件**：元数据/血缘服务、版本服务、质检网关、回归评测服务、合规引擎
- **接口**：版本晋升申请 → 门禁审批结果；血缘查询 API
- **业内参照**：Voxel51 数据集版本与修改追踪 + 版本快照；RoboLineage 类型化血缘制品

### ⑤ 资产域（数据集资产）

- **职责**：数据集目录（检索/打标/浏览）、统一湖仓存储（原始文件+元数据+向量）、不可变快照、版本回溯、训练样本快照
- **组件**：数据集目录服务、湖仓（DLF 式统一管理）、向量检索、快照服务
- **接口**：数据集资产 API（查询/导出/快照）
- **业内参照**：阿里云 Agentic Lakehouse（DLF 统一原始文件+向量+元数据）

### ⑥ 消费域

- **职责**：训练消费（数据集导出→分布式训练）、下游评测、Badcase 回流驱动数据迭代
- **组件**：数据集导出服务、训练衔接（Ray Train/Tune）、下游评测服务、回流通道
- **接口**：训练数据集 + 评测报告 → 回流样本
- **业内参照**：GigaBrain 多阶段 QC 后接训练

### 横切层

| 横切 | 能力 |
| --- | --- |
| 可观测性 | 指标（吞吐/失败率/成本每样本）、算子级追踪、日志、告警 |
| 安全合规 | 脱敏（可前插）、权限（RBAC）、审计日志、数据出境合规 |
| 多租户与计量 | 配额（ElasticQuotaTree）、优先级、计费、隔离 |

## 4. 数据流与元数据流（双流）

**主数据流**（数据管道）：

```
接入域 ──原始数据──► 生产域 ──结构化数据集──► 资产域 ──训练集──► 消费域
   ▲                                                │
   └────────────── Badcase 回流（消费→治理→生产）──┘
```

**元数据流**（登记与治理）：

```
每一步执行 → 登记 血缘节点 + 数据集版本 + 算子版本 + 指标 → 治理域元数据服务
门禁晋升 → 资产域快照 → 消费域读取版本 → 评测报告回流治理域
```

**关键点**：数据流是"产物流动"，元数据流是"审计与治理"——两者分离，但通过血缘图关联。

## 5. 关键机制

1. **版本三锁**：数据版本 + 算子版本 + 模型版本，一次产出完整锁定，可复现
2. **不可变快照**：数据集版本发布即冻结，训练引用精确到版本
3. **门禁晋升流**：规则校验 → 双模型互检 → 分层抽检 → Golden Set 回归 → 发布审批（任一环节失败不得晋升）；算子/阶段级落点 = [算子设计-02](算子设计/算子设计-02-算子接口规范与质量门体系.md) 的 G0–G6 质量门
4. **声明式控制循环**：用户声明期望数据集 → 管控域调度执行 → 治理域校验 → 资产域发布
5. **四层数据隔离**：训练/验证/测试/回归集在治理域强制隔离，防泄漏

## 6. 演进路径（四阶段）

| 阶段 | 重点 | 交付 |
| --- | --- | --- |
| **P1 MVP** | 单源接入 + 关键算子（感知/封装）+ 资产版本 + 单格式消费 | 端到端能产出一版可训练数据集 |
| **P2 控制面完整化** | KubeRay + 调度 + 状态机 + 血缘 + 门禁 | 多作业并行、失败自愈、版本可审计 |
| **P3 规模化** | 多源工厂、多租户、计量计费、湖仓检索、合规 | 平台化运营、多团队共享 |
| **P4 智能闭环** | Badcase 回流驱动自动补采、评测驱动数据迭代 | 数据-评测-补采自动闭环 |

## 7. 架构要点总结（总设计师话术）

> "我把平台切六域：接入管采集、生产跑算子、管控做编排调度、治理管版本血缘门禁、资产做湖仓快照检索、消费管训练评测回流；可观测、安全、多租户三层横切。核心机制是数据集为中心的不可变版本 + 门禁晋升 + 血缘制品化——数据从原始信号到训练资产全程可追溯、可复现、可迭代。控制面和数据面严格分离，这是它和传统数据处理平台最大的区别，也是它作为'数据工厂操作系统'的骨架。"
