## 1. 逻辑算子、物理执行单元与 RayJob

| 层 | 职责 | 示例 |
| --- | --- | --- |
| 逻辑算子 | 定义输入输出、版本、依赖和独立质量检查，形成可追溯 DAG | 解码重采样、去畸变、深度、相机位姿 |
| 物理执行单元 | 一次 task 或一个 Actor 中的一段调用，声明资源、批次和恢复边界 | 一次解码后在同进程完成去畸变；一个 GPU Actor 内依序执行深度和位姿 |
| RayJob | KubeRay 的提交和生命周期边界，入口可编排多个物理单元，并重复调度其批次 | 一次批量 Ego 重建提交，驱动多个 CPU 批次及 GPU Actor 池 |

融合计划以显式算子依赖为输入。物理单元内按拓扑序执行，每个逻辑算子仍记录状态、版本、逻辑输入输出哈希和算子指标，质量门仍在原语义位置判定。物理边界改变后，要验证原有分支、门禁和血缘可从日志与清单还原。[算子设计-02](算子设计-02-算子接口规范与质量门体系.md) · [算子设计-04](算子设计-04-算子血缘与版本三锁.md) · [KubeRay RayJob 文档](https://docs.ray.io/en/latest/cluster/kubernetes/getting-started/rayjob-quick-start.html)

- 优先合并资源类型相同、顺序依赖稳定、批次粒度兼容且中间结果复用范围较小的步骤。核算实际省下的调度、重复解码、序列化、网络传输和存储往返。
- 遇到独立扩缩容、外部复用、人工审核、重算代价高或快慢任务混杂时，保留独立执行或恢复边界。扇出和汇聚处显式保留依赖，避免为了合段把本可并行的分支全部串行。
- 默认沿用 Ray Data、GPU Actor、RayJob 和 KubeRay。Daft 作为列式批处理执行候选，后续可围绕扫描、批量转换和写分片与现有 Ray Data 路线做同输入对照，比较内存、I/O、质量等价与恢复代价。

融合评估从单算子、执行单元、整条管线取三组数据。算子耗时按输入规格分层，执行单元额外记录调度等待、装载和搬运，整条管线覆盖质量门和提交。若单算子变快而其输出队列持续增长，先确认相邻阶段的服务速率和共享资源是否饱和，再调整融合边界或扩容。

## 2. 整机资源与队列

### 2.1 CPU 准入与实际线程预算

对同一个执行单元，记 `r_i` 为步骤 `i` 的逻辑 CPU 请求，`r_base` 为该单元常驻辅助工作的逻辑预算。用可能同时运行的步骤集合 `A` 估算单元请求，再在节点上核算所有活跃单元。

```text
r_unit = r_base + max_A(sum(i in A, r_i))
sum(u in running_units, r_unit(u)) <= C_ray_node
```

纯串行、且每步线程池的工作确实停止后才切换时，步骤部分取 `max_i(r_i)`。解码预取、推理准备、异步编码或 Actor 内多批并行如果能重叠，重叠部分需要按并行和计入。Ray 调度预算和 Kubernetes Pod CPU request/limit 分别配置，确保整个 worker 留有运行时和数据搬运余量。

另记 `p_u(t)` 为单元 `u` 在时刻 `t` 的 CPU 活跃并行度预算，包含解码、OpenMP/BLAS、框架线程池、预取与子进程。用下面约束选择初值，按整机观测调整。

```text
max_t(sum(u in running_units, p_u(t))) + P_system_reserve <= P_effective_budget
```

`P_effective_budget` 结合 Pod 可用 CPU 时间、节点可用核和负载条件估计，`P_system_reserve` 留给系统、Ray 运行时及搬运。显式设置 Actor 的 `num_cpus`，并独立配置 FFmpeg、OpenCV、PyTorch 和 OpenMP/BLAS 的并行度，记录 CPU 实际用量、可运行线程、上下文切换和 Pod throttling。Ray 的 `num_cpus` 主要用于调度准入，线程由库和操作系统调度，数量与 CPU 用量需要分别观测。[Ray 逻辑与物理资源](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html#physical-resources-and-logical-resources)

### 2.2 GPU 模型常驻与串行装卸

| 形态 | 适用与开销 | 验证点 |
| --- | --- | --- |
| 同卡同 Actor 常驻多个模型 | 依赖紧、模型组合固定且显存足够时，摊薄加载成本并复用同进程张量 | 常驻权重、最大样本形状、并发批次、保留中间张量、工作区和分配器峰值 |
| 同卡串行加载和卸载 | 显存只允许模型逐段运行时，以装卸及同步时间换可运行性，可按受控批次摊销加载 | 权重冷读/热读、加载和卸载 P95、卸载后存活引用和显存、端到端吞吐 |
| 分模型 Actor 池 | 模型速率差异大或有独立扩容需求时，按阶段供给 GPU | 阶段队列、网络及主机内存拷贝、重复读数据的代价、负载偏斜 |

显存预算以并发峰值为准。同卡常驻时纳入全部常驻权重，再计同一时刻活动批次的峰值、跨步骤还活跃的张量和余量。串行装卸还需验证上一阶段张量/上下文是否存活，`empty_cache()` 只针对分配器的空闲缓存，批尾记录 `allocated`、`reserved` 与设备峰值。若不能稳定回收，可用分进程边界并测量重启代价。Ray GPU 资源声明用于调度，实际显存与并行度另设预算。

### 2.3 CPU/GPU 分队列与节点复用

- CPU 队列承接扫描、规则过滤、解码预处理、对齐和封装，GPU 队列承接模型调用。分别看队列龄、积压和服务速率，CPU 供给按 GPU 消耗速率调节，避免 GPU 等数据或在 CPU 侧积存大量帧。
- GPU worker 同样为推理预取、主机到设备传输和进程运行预留 CPU。剩余 CPU 可按租户配额承接短时、可延迟的轻量任务，例如索引校验或元数据汇总。以独立队列和 worker 资格约束进入，用 Ray 自定义资源和并发槽控制准入，并配置 CPU、内存、I/O 预算。
- 当推理就绪队列增长、GPU 等输入、CPU throttling 或 GPU P95 恶化时，停止向 GPU 节点派发轻量任务，让已有短任务排空或按编排策略收回。复用开关需做同负载对照并保留回退到专用 CPU 池的路径。池归属、配额和优先级见 [03-管控域](../../03-管控域/README.md)。

## 3. 数据路径、持久化与背压

| 数据路径 | 适用场景 | 主要约束 |
| --- | --- | --- |
| 进程内缓冲或张量 | 融合单元内的短寿命结果 | 以生命周期和批次控制峰值，及时释放分支已消费的中间态 |
| Ray ObjectRef | 同一 Ray 集群内的批次交接 | 同节点读取对象存储中受支持的只读对象，例如 NumPy 数组，可避免反序列化时的数据复制。跨节点拉取会走网络，仍可直接用 ObjectRef 传输。对象写入、格式转换及 CPU↔GPU 搬运另计 |
| 节点本地缓存 | 可重建的模型权重、编译产物、短期工作文件 | 生命周期随节点及卷配置，记录命中、驱逐和重建代价 |
| OSS/S3 检查点或数据分片 | 可恢复批次、跨作业交付、人工审核和发布制品 | 通过提交清单引用分片，恢复按已校验的清单读取 |

跨节点传递是否持久化由故障范围、重算代价、复用周期和交接契约决定。同集群的对象可跨节点拉取，跨独立作业和故障域交接优先用可恢复制品。Ray 对象溢写计入资源压力和 I/O，持久恢复仍依赖可提交、可校验的检查点。[Ray 对象序列化](https://docs.ray.io/en/latest/ray-core/objects/serialization.html#numpy-arrays)

- 以批次或分片承载多条样本，保持视频与结构化记录的样本 ID、帧号或时间偏移索引。可共享解码则复用帧批次，需持久化时优先聚合视频和结构化列，避免每帧一个小文件。以对象大小分布、对象数、读写请求率、P95 延迟和局部读取放大决定分片粒度。
- 恢复边界优先选重算昂贵、输出可复用、门禁后可独立验证的批次。记录上游输入哈希、算子及模型三锁、可见的门禁结论和分片校验信息。调整检查点间距时同时测写读成本、受故障影响的重算量和恢复时间。
- 每条边同时限制在途批次数和字节，按高低水位停发和恢复。下游落盘变慢、对象存储接近水位、GPU 队列满或门禁等待时，收缩上游拉取/提交窗口。对变长片段按估计帧数或字节做批次预算，对超大样本单独限额或分段。扇出共享对象等所需分支完成后释放，汇聚也限制等待中的未配对结果。

在途额度在提交前预留，写入或交接完成后随对象生命周期归还。为汇聚所需的分支与检查点写入留出独立额度，防止同一个上游队列占满缓冲后阻塞提交。采集软水位触发时长及等待归还额度的 P95，以区分正常限流和处理堵塞。

## 4. Ego 生产链路的融合示例

该方案从已通过 G0 的 Ego 原视频清单出发。以下编号是物理执行与恢复边界示意，GPU 常驻和 CPU 资源请求由整机基准决定。完整业务 DAG 可在同一个 RayJob 内编排。

| 物理执行单元 | 输入 → 输出 | 资源与融合理由 | 可恢复边界 |
| --- | --- | --- | --- |
| CPU 预处理 | 视频清单、内参 → 校正帧批次和帧索引 | 一次解码关联重采样、去畸变，按帧时间戳绑定内参 | 原始输入清单已持久化，帧批次先走内存或 ObjectRef，失败从原始批次重算 |
| 脱敏与 G1 | 校正帧 → 脱敏帧、覆盖及遮挡记录 | GPU 检测与轻量 CPU 模糊处理，按依赖做 G1 验收 | G1 通过后视复用和重算代价将脱敏视频分片及帧索引持久化，未过门数据仅在授权范围内处置 |
| GPU 感知 | 脱敏帧、内参与片段元数据 → 深度、相机位姿、手部及可选物体分支 | 一条链保留深度先验 → 位姿/FoV → 手部的依赖，检测/分割/跟踪分支按负载独立排队，6DoF 按需等待 RGB-D 与位姿 | 同执行单元保留短寿命中间张量。需跨单元、独立重试或被多处复用的结果可按批写检查点 |
| CPU 对齐及 G2 | 各路结果和时间索引 → 统一坐标与时间基准的结构化片段 | 在汇聚后完成动作对齐和 G2 校验 | 按批提交结构化分片、质量记录和血缘，恢复可复用已过 G2 的片段 |
| 语义、质检与封装 | 结构化片段、视频 → 标注、质检报告、候选数据集分片 | GPU VLM 与 CPU 清洗/编码/封装分别排队。G3/G4 及人工审核按契约推进，G5 校验封装 | 分片暂存后形成候选清单。治理按 G6 晋升不可变版本 |

### 字段示意

物理执行计划引用 `PipelineSpec` 中的逻辑算子 ID。下面只示意心跳、重试和基准所需的计划字段，具体请求和预算由实测填入。

```yaml

operator_ids: [op-per-depth, op-per-cam, op-per-hand]
execution: gpu-actor
depends_on: [ego_desensitize_g1]
```

## 5. 失败处理与发布可见性

1. 单元按批次至少执行一次。重试以稳定输入清单、逻辑算子和配置版本推导幂等键，从最近一个已提交检查点恢复。进程内结果、已失效的 ObjectRef 或未提交的分片按对应边界重算。
2. 瞬时失败退避重试。稳定复现的显存不足先降并行度，或切换已经质量核验的执行布局。结构性错误终止并上报，数据性失败按算子设计-03 进 DLQ/人工通道。取消释放在途预算，取消或租约过期的执行尝试失去提交资格。
3. 每次执行写到 `attempt_id` 作用域的暂存位置。校验清单覆盖范围、文件完整性、哈希和对应质量门，通过后用事务目录或条件更新一次性提交清单引用。同一幂等键的并发尝试只允许一个提交者，冲突时读取已提交清单并核对版本和输入。
4. 读取方沿已提交清单取分片。阶段检查点面向内部恢复，候选版本还须经治理晋升才能面向消费侧。提交前中断只留下暂存对象，提交后响应丢失则按幂等键查询结果。回收只处理确认未被任何有效清单引用的到期对象。

## 6. 指标与基准矩阵

固定任务分布、质量门、统计边界和稳态窗口。令 `T_n` 为配置 `n` 张 GPU 时的稳态吞吐，同一指标下计算加速比 `S_n = T_n / T_1` 和扩展效率 `E_n = S_n / n`。单卡需有可运行且质量等价的基线。GPU 推理用推理出口的样本/小时诊断阶段效率，整条流水线用通过指定门禁并已提交的有效数据小时/墙钟小时计算另一组 `T_n`、`S_n`、`E_n`。有效数据时长、去重及计费沿用 [算子设计-06](算子设计-06-算子成本模型.md)。

| GPU 数 | 冷启动（cold） | 稳态（warm） | 对照 |
| --- | --- | --- | --- |
| 1 | 作业提交到首个合格批次可见、固定输入批完工时间 | 推理吞吐、有效吞吐与延迟基线 | 未融合 / 融合，串行装卸 / 同卡常驻（显存可运行时） |
| 2 | 同口径计启动、模型加载与首批可见 | 两卡 `T_2`、`S_2`、`E_2` | 相同布局做纵向扩展，记录实际卡与节点位置 |
| 4 | 同口径计时并区分节点缓存命中 | 四卡 `T_4`、`S_4`、`E_4` | 能部署时对照单机与跨节点版本，标注网络和存储拓扑 |
| 8 | 同口径计时并记录并行冷启动的读压力 | 八卡 `T_8`、`S_8`、`E_8` | 分开测固定共享 CPU/存储预算与按卡数扩配，记录瓶颈迁移 |

### 6.1 对照方案

在 1/2/4/8 卡各跑一轮未融合基线和一轮融合计划，每个单元格包含独立重复的 cold 与 warm 试验。横向计算同卡数的融合收益，纵向用各自布局的一卡结果作为 `T_1`。显存不足或特定拓扑无法部署时标注原因。测试独立扩容布局时记录每个资源池分配的卡数，整条管线的 `n` 为全部参与执行的加速卡总数。

| 对照变量 | 固定项 | 主要观察 |
| --- | --- | --- |
| 模型串行装卸 / 同卡常驻 / 分池 | 模型权重、输入分层、门禁与输出 | 模型加载时间、显存峰值、队列等待、实际跨阶段拷贝 |
| 线程预算与节点 CPU 复用开关 | 卡数、GPU 执行布局、输入任务顺序 | CPU throttling、GPU 等输入、推理 P95、有效吞吐及轻量任务完成量 |
| 分片大小与检查点间距 | 融合布局、输出模式及故障注入位置 | 请求数、写放大、重算量、恢复时间、有效吞吐 |

### 6.2 采样与判读

- **可比条件**。固定 GPU 型号、单节点 CPU/内存与网络规格、运行时镜像、模型权重、解码参数、输出格式及门禁。使用同一数据快照和长度、分辨率、场景分层，保证输入足以填满稳态窗口。把批大小、线程、Actor 数、实际节点拓扑及 CPU/存储预算写入实验记录。每次变更一组因素并与基线成对运行。
- **冷暖与重复**。冷态明确清空或隔离的缓存层，记录镜像拉取、权重下载、扩展初始化和首批输出。暖态在模型、队列和缓存进入预定状态后用固定窗口观测。每组独立重复，保存原始样本、运行次数、输入数量和计时边界，报告吞吐中位数及离散度、延迟 P50/P95/P99，尽量交错运行基线和实验组，标注高分位的样本量。上述指标及配置阈值待实测。
- **等价检查**。核对输出样本集合、时序、分片覆盖、门禁通过/淘汰和人工分支。确定性步骤比较逻辑内容哈希，模型输出按预先约定的容差和 Golden Set 判定。异质任务按片段长度和来源分别报吞吐及延迟，汇总沿用固定任务分布。
- **归因与故障对照**。记录 GPU 忙闲和等待输入、设备显存、CPU 竞争和线程、队列龄/字节、跨节点传输、对象溢写、对象存储读写及小文件、重试和重算量。GPU 推理吞吐上升而有效产出停滞时，结合指标定位 CPU 供给、写入背压、门禁耗时和筛除比例。用 worker 中断、下游限速及写入中断验证恢复耗时、终态完整性、重复提交去重和背压生效。

| 观测 | 归因线索和复测 |
| --- | --- |
| GPU 空等且预处理出队追不上 | 比较解码 CPU 时间、网络读和有效 CPU 预算，单独改变预处理供给或关停轻量复用 |
| GPU 满载且 GPU 等待队列增长 | 分阶段核对推理时间和显存余量，测独立扩容或调批后的端到端变化 |
| 写出积压伴随小对象请求增多 | 对照合并分片和请求时延，确认变更后恢复范围和训练侧读取形态 |
| 同类输入推理变快，但质量门耗时或淘汰率上升 | 分别对账门禁等待和输出等价，复测有效产出与恢复成本 |
