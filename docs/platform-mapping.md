# 业界工作流平台映射

三个平台分两层：胜算/火山 LAS 是**数据层工作流**（数据怎么被加工）；百舸工作流是**算力层工作流**（加工任务怎么被调度执行）。本项目在单机上同时复刻了两层的骨架——数据面算子对应数据层，控制面调度对应算力层——因此映射到任一平台都是"组件对号入座"，不是重新设计。

## 平台组件对照（2026-09 调研）

| 本项目组件 | 百舸工作流 | 火山 LAS | 百度胜算 |
|---|---|---|---|
| face-blur 算子（视频→脱敏视频） | 工作流节点/任务 | 数据处理任务 | 算子能力 |
| split→blur×N→merge→qc | DAG 组件化编排 | 工作流添加任务编排 | 数据处理管线 |
| 无状态 Worker + 队列 | 任务式作业（按需挂载/释放） | LAS 托管调度 | 平台托管 |
| gocp（Go 控制面服务）+ Python 算子 Worker | 平台调度控制面 + 算法任务容器（业界标准分工） | 同左 | 同左 |
| 原子 Join 门控 | DAG 依赖边（平台原生保证） | 同左 | 同左 |
| 状态机+重试+lease | 任务生命周期管理+自动重试 | 平台托管 | 平台托管 |
| stats 命令（排队/处理分位、吞吐、失败率） | 可观测：metrics-server / Prometheus | 监控大盘 | 平台指标 |

| qc 抽帧复检算子 | DAG 中的质检节点 | 数据质量任务 | 算子 |

## 通用引擎能力对照

通用工作流引擎（Airflow / Argo / Temporal / K8s Job）与本项目在三个维度上各自的做法：

- **调度语义**：引擎用中心调度器 + DAG 依赖边派发任务；本项目用 SQLite 事务实现同语义——`BEGIN IMMEDIATE` claim 互斥 ≈ 单写者串行化，原子 Join ≈ fan-in 依赖边，lease TTL 回收 ≈ SQS visibility timeout。语义同构，存储可换件。
- **容错**：引擎标配重试策略 + 心跳续约 + 死信队列；本项目是 at-least-once + 幂等算子（失败留半成品无害，重跑覆盖）+ attempt 上限（默认 3）+ qc_failed 不自动重跑（确定性系统原参数重试无效）。lease 心跳与 DLQ 是已知的合法简化。
- **可观测**：引擎标配时序指标（Prometheus）+ 大盘 + 告警；本项目以 `stats` 命令收口最小出口（排队/处理 P50/P95、吞吐、失败率、重试计数，只读旁路直读库文件），时序化留平台期。

实施计划 Context 的 14 项逐项审查结论：**骨架同构，无缺口级差距**——分层、任务模型、调度语义、容错模型、质检闸门全部与业界通用形态一致；剩余差距集中在平台配套（lease 心跳续约、DLQ、血缘、分层抽样、容器化、观测时序化），全部记为演进项不进 MVP。这份差距清单就是"轻量 demo → 业界平台"的距离，也是本文档的价值。

## 控制面/数据面演进

- **控制面**：SQLite 状态库 + 调度函数 → （自管模式）gocp Go 服务 → （全托管模式）平台工作流引擎。
- **数据面**：Worker 子进程 → Docker 任务容器（百舸任务式作业，按需挂载/释放）。

上平台后，队列 / Join / lease / 状态机 / 重试全部被平台收编（这些正是平台原生能力）；**保留的是算子内核、质检判定逻辑、阈值与参数策略**——迁移时换的是调度层，保留的是算子层。

## 具身数据链路定位

采集 → **脱敏（本项目）** → 入湖 → 标注 → 训练。

本管线是具身数据合规的第一道工序：采集侧产出的海量视频必须先过人脸脱敏才能入湖进入标注/训练。位置在链路最前端，决定了它必须以批处理工作流形态存在（量大利不出实时价值），也决定了它的平台化归宿是数据层工作流的第一个算子节点。
