# BUG-010：qc 抽帧走 `-vf fps` 滤镜——相位偏移 + 时间戳失真

- **日期**：2026-09-24
- **发现场景**：真实手机视频脱敏后 qc 报 34/71 违规；追查违规帧内容时发现
  qc 抽中的帧并不在它声称的时间戳上——标签整体偏 +0.47s，且抽样相位
  恰好与内核检测节奏锁相，违规样本全部落在纯预测帧上。

## 现象（像素级 MSE 定谳）

`FFmpegReader(path, sample_fps=1.0)` 原实现给 ffmpeg 加 `-vf fps=1`。
对 30fps 源（含我们自己的 CFR 重编码输出）实测：

- fps=1 输出的第 k 帧 == 原始第 `30k+14` 帧（MSE=0.0 精确匹配，源与输出两侧一致）
- 恒定 +14 帧 ≈ 0.467s：`qc 标注 t=k` 的违规实际发生在 `t=k+0.467`
- 容器流 PTS 从 0.000000 开始、落在 1/30 网格上——滤镜为何选 30k+14
  而非 30k，机制未查明（疑似与容器 edit-list/音频流有关），但偏移量
  被精确测定且可复现

## 危害（两层）

1. **时间戳失真**：违规标签错位 +0.47s，人工复核找不到帧。
2. **相位不受控**：qc 抽样相位由 ffmpeg 内部行为决定。本例 30k+14 ≡ 2
   (mod 3)，恰好全部落在内核（det_every=3）的纯预测帧上——qc 看到的
   违规分布是滤镜相位的产物，不是视频的真实漏糊分布。换一个容器
   相位就变，结果不可复现。

## 修复

`ffmpeg_io.py FFmpegReader`：不再用 fps 滤镜，全帧解码 + Python 帧号
跨步抽样——步长 `N = round(fps / sample_fps)`，每个窗口取中点帧
（`i % N == N//2`）。抽样帧必然是原始帧序列的逐帧成员；时间戳由
`qc.py` 按 `(i*N + N//2) / fps` 精确还原。`sample_fps=None` 走同一
代码路径即得全密度逐帧复检（最终验收用）。

## 教训

- 抽样工具必须自己掌控抽样相位与时间戳换算；把两者都委托给滤镜，
  滤镜的实现细节就成了质检结果的一部分
- 质检抽样与被测系统的节奏锁相（stride ≡ 0 mod det_every）会让
  1fps 抽查系统性偏向某一类帧——抽查通过≠没漏，最终验收用全密度
